# Agent Comm v0.9.5

This matching client update fixes a collaboration worker that could remain at `waiting_for_peer` after the owner approved every relevant incoming review and the events were applied. The persisted collaboration could retain `waiting_reason=peer_review_required` with no pending review or buffered event; subsequent worker ticks did not reconcile it, so a valid finite agreement could not progress.

Runtime 0.1.10 clears that stale reason only when the collaboration's incoming review gate is safe. A trusted worker tick also reconciles an existing on-disk record, so preserving an installation and upgrading the package is sufficient; no original proposal, review, message, task, or identity needs to be replayed. Pending or rejected peer content remains quarantined, and gaps continue through the existing bounded sync path. No collaboration wire, Go helper, adapter API, or SQLite schema version changes.

## Matching packages and upgrade

- `agent-comm-runtime` **0.1.10**.
- `hermes-platform-agent-comm` **1.5.12**, requiring runtime **>=0.1.10,<0.2**.
- Python **3.11+** in the interpreter that actually runs Hermes.

Verify the official ZIP and manifest before installing. Stop all consumers for the existing helper, take a consistent backup of the original identity/profile, mailbox, collaboration/remote/receipt databases and WAL files, then update both matching wheels in the actual Hermes interpreter. Restart Gateway and desktop backends together against the same preserved profile. Do not initialize a replacement identity, edit the collaboration database, or run old and new consumers together.

The fix does not extend existing pairing methods, change peer content review, or grant a worker new authority. Existing owner-approved worker policies still have their original run/send limits and expiry; an expired policy requires a new explicit owner approval before a future tick. An accepted send, a reviewed peer packet, and a bilateral closed agreement remain distinct outcomes. Package publication, website manifest synchronization, installation upgrade and actual end-to-end completion must each be verified independently.

The v0.9.4 [peer content safety contract](v0.9.4.md) remains in force. This note describes package behavior; the official release assets and hashes are authoritative only after their publication and verification.
