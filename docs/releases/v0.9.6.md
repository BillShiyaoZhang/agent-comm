# Agent Comm v0.9.6

This matching client update lets an owner refer to several collaboration tasks in one console turn and inspect a task independently of a conversation. `conversation.send` accepts up to eight structured `mentions` with `kind: "task"` and an owner-visible `task_id`; `conversation.get` returns those references on the turn. A mention provides context to the agent and does not authorize an operation, a peer message, or a review. Existing `turns[].related` continues to identify actual operation provenance separately.

The new paired read methods `task.list`, `task.detail`, and `task.events` expose owner-scoped task discovery, a bounded current snapshot, and a paged timeline with stable cursors. Detail also includes references to turns from the current paired console. Event records distinguish local transitions, reviewed peer protocol activity, visible messages, and console turns. Reads remain subject to explicit pairing capabilities; an existing pairing receives no new methods until the owner approves an updated pairing. Task IDs are checked against the paired owner before storage or retrieval.

History coverage is explicit. The local transition journal starts when the new runtime is installed, so older approval and operation changes cannot always be replayed exactly. It retains status metadata, not raw approval questions, actions or peer wire content that might later become hidden by a review or blocking decision. A current detail snapshot may show an approval question only while the current peer-content gates permit it. Large sections or fields are bounded and reported through `coverage.truncated`; `coverage.complete` remains false where historical fidelity is unavailable. The timeline reports source and timestamp for each returned item, and only owner-visible content is included. A submitted action, helper ACK, review, and completed collaboration remain distinct states.

## Matching packages and upgrade

- `agent-comm-runtime` **0.1.11**.
- `hermes-platform-agent-comm` **1.5.13**, requiring runtime **>=0.1.11,<0.2**.
- Python **3.11+** in the interpreter that actually runs Hermes.

Verify the published ZIP and manifest before installing. Stop consumers of the existing helper, take a consistent backup of the preserved identity/profile, mailbox, collaboration/remote/receipt databases and WAL files, then update both matching wheels in the Hermes interpreter. Restart Gateway and desktop backends together against that profile. Do not initialize a replacement identity or run old and new consumers together. The local task history table is added to the existing runtime database during upgrade.

For an existing installation, the owner must explicitly grant `task.list`, `task.detail`, and `task.events` in the pairing flow to use those reads. Pairing repair should preserve the current console and helper identity. Package publication, website manifest synchronization, installation upgrade, and real host verification require separate evidence; this source note alone does not establish any of them.
