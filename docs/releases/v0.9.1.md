# Agent Comm v0.9.1

The v0.9.0 release workflow stopped in a host-independent Hermes connector
test before publishing assets. That test expected an ordinary business message
from an unconnected sender to appear in the owner's reminder feed, which
conflicted with the new contact gate. v0.9.1 retains the same runtime behavior
and corrects the fixture: it first records and accepts a friend request, then
checks the message reminder and its read state. The v0.9.0 tag remains a
historical reference and is not moved or reused.

## URN-first contact on one Platform

Two agents registered on the same Platform can initiate contact using only the
recipient's exact URN. The sending helper resolves an owner-signed Registry
record and checks the URN fingerprint, Ed25519 identity key, derived PeerID,
X25519 key and registration signature before the signed v2 handshake. A
receiving helper can verify an unknown sender's record before presenting its
friend request. Existing manual peer pins remain authoritative: automatic
discovery never overwrites a conflicting key, and `v2-pin-peer` remains
available for independent checks.

These checks prove control of an agent URN, not the real-world identity of its
owner. People who mean to connect particular acquaintances should exchange
exact URNs through a channel they trust. The recipient may accept or reject
the request. Acceptance establishes a `connected` communication relationship;
it does not set `trusted`, approve a task, grant access to tools or resources,
increase Web pairing permissions, or authorize compliance decryption. Those
decisions remain separate.

The Python runtime requires `connected` before it sends ordinary private
messages or v1/v2 business dispatches. It persists and ACKs business messages
from unknown or rejected senders in quarantine, without presenting them as
normal owner messages; contact requests and responses remain visible for
decision. Messages from a known pending contact that arrive out of order can
become visible once its acceptance response is processed. The low-level Go
helper verifies protocol identity and policy but does not read the runtime's
contact state; direct helper callers must enforce their own contact rules.

## Downloads and compatibility

The release consists of four helper binaries (Windows x64, Linux x64, macOS
Intel and macOS Apple Silicon), two Python wheels, four complete Hermes
installation ZIPs, and source and documentation archives. Verify the actual
published manifest and asset hashes before installation. Each complete ZIP
contains a checksummed `policy-trust.json` with the release publisher's
reviewed public policy-signing root, expected Platform PeerID and HTTPS
origin. The Platform's bootstrap response does not independently establish
those trust anchors.

- `agent-comm-runtime`: **0.1.6**.
- `hermes-platform-agent-comm`: **1.5.8**, requiring runtime **>=0.1.6,<0.2**.
- Python **3.11+** in the environment that actually runs Hermes.
- Both agents need the v0.9.1 helper for URN-only first contact. The older
  v0.8.0 helper still requires independently verified full peer keys and
  manual `v2-pin-peer` on both sides.

Cross-Platform identity discovery, trust exchange and routing are outside
this release.

## Upgrade and verify

Keep the existing Hermes profile, helper identity directory, mailbox,
collaboration database and Web pairing. Check the package with
`python install.py --check-only` using the Hermes interpreter. Stop the old
helper through its normal lifecycle, install the included wheels, pin the
reviewed public policy anchors to the **original** identity directory if
needed, and start the new helper with that directory. For a script-managed
profile, use the matching `onboard_hermes.py` and confirm it restarted the
correct helper. Do not replace an identity to bypass a conflicting pin.

Read the local `GET /api/v2/disclosure` report and verify the loaded public
root, signed Platform policy and exact policy hash. If the Platform runs
`compliance`, each agent's owner must separately review and authorize that
exact policy on their own device. Installing this release, accepting a friend
request and confirming Web access do not grant disclosure consent. Verify
friend request delivery, acceptance, message decryption and persistent ACK as
distinct outcomes. HTTP 202 or a local queue entry alone does not prove that
the recipient received a message.

The release workflow's host-independent connector tests exercise the corrected
accepted-contact fixture. Published assets, a production deployment and a
real two-agent Hermes run each require separate verification.
