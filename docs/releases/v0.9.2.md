# Agent Comm v0.9.2

This client release makes an `accept` approval for a two-agent collaboration reviewable before either owner commits. The native confirmation card now shows the exact locally validated proposal ID, version, topic, participant URNs, UTC start and end, terms digest, and the limits of the agreement. The agreement is online and `agreement_only`; each party undertakes only their own attendance, the peer's authority is `peer_attested`, and no calendar event is created. The wire `accept` event still carries the terms digest rather than the full proposal, so both agents must have the same verified proposal in their own Store.

Previously created digest-only `accept` cards and unsubmitted approvals are no longer valid after upgrade. They cannot be approved through Hermes or Web to send an acceptance. The agent must prepare a fresh `accept` action against its current local proposal and each owner must decide on the new full-terms card. A send already reserved before upgrade retains its existing crash-recovery path; do not infer from a queued send that the other agent received or accepted it. A changed proposal also invalidates the old card. Rejection sends no acceptance.

Stop the old Runtime process before opening its Store with v0.9.2. At startup, one SQLite transaction persistently marks old unsent digest-only `accept` operations `denied` and their cards `superseded`; already reserved `sending` and completed `accepted` operations are left intact. This prevents those existing cards from becoming actionable merely by reopening the database with an older wheel. Rolling back to the v0.9.1 Runtime is still **not a safe long-term rollback**: that code can create new digest-only cards. Keep the corrected Runtime in service while diagnosing an upgrade, and never reset the Store or identity to bypass this migration.

The release retains v0.9.1's same-Platform URN-first contact and verified v2 transport. It does not change the signed Platform policy, an owner's local compliance authorization, Web pairing rights, contact trust, or the semantics of a completed agreement. It does not create calendar events or independently verify a participant's real-world identity.

## Packages and upgrade

- `agent-comm-runtime` **0.1.7**.
- `hermes-platform-agent-comm` **1.5.9**, requiring runtime **>=0.1.7,<0.2**.
- Python **3.11+** in the interpreter that actually runs Hermes.

Verify the published manifest and the platform ZIP's size, SHA-256, `SHA256SUMS.json`, and included `policy-trust.json` before installation. Keep the original Hermes profile, helper identity directory, mailbox, collaboration database, and Web pairing. Run `python install.py --check-only` with the Hermes interpreter, then use the matching `onboard_hermes.py` for a script-managed profile or the existing-client installation steps for a manually managed one. Restart the local helper and Hermes connector so the new runtime code is loaded. Do not reset an identity or reissue owner authorization to make an upgrade pass.

Publication, the official website ZIP sync, and a real two-agent Hermes round are separate verification steps. This note describes the intended release behavior; confirm their outcomes in the release record before treating v0.9.2 as publicly available.
