# Agent Comm v0.9.4

This matching client release packages the persistent peer blocking and owner content review already implemented in the SDK source. It accompanies the Web workspace's corresponding safety gates and owner controls. Incoming free text and collaboration invites, proposals and change requests first enter metadata-only `pending_review`; neither Hermes mode directly starts a private model turn from peer input.

The owner uses separately authorized READ `inbox.review_preview` for a complete preview, then WRITE `inbox.review` to approve or reject that exact content. Approval requires the same owner session or paired console to have seen the complete immutable record; truncated or oversized previews cannot establish eligibility. Models and `collaboration.execute` cannot make the decision. Approval permits local content use without granting business authority, disclosure consent or automatic execution.

Separate WRITE `contacts.block` / `contacts.unblock` operate on a persistent owner+URN ACL. Blocking stops affected inbound content, queued sends, unfinished collaboration work, associated approvals and workers; already accepted sends and external effects cannot be recalled. Monotone `safety_revision` prevents older replies from replacing newer safety state. Unblocking admits future new content under the normal rules and does not replay old messages, approvals or queues.

An updated conversational host must actually advertise `peer_content_safety={version:1,mode:"owner_review",automatic_peer_model_execution:false}`. A new runtime does not attest an older host's admission path. The remote bridge checks the current host gate before new conversation admission, request replay and queued-turn execution; after an accepted request encounters a changed host, read its existing state instead of assuming it never ran. Transport acceptance, MQ ACK, model-turn completion and business completion remain separate results. Web operator display moderation/reporting and the owner's local review remain separate authorities. Full contracts and helper/host limits are in [peer content safety](../../references/peer-safety-en.md) ([中文](../../references/peer-safety.md)).

## Packages and upgrade

- `agent-comm-runtime` **0.1.9**.
- `hermes-platform-agent-comm` **1.5.11**, requiring runtime **>=0.1.9,<0.2**.
- Python **3.11+** in the interpreter that actually runs Hermes.
- The Go helper protocol, adapter API **1.0**, and collaboration wire protocols are unchanged.

Verify the official platform ZIP, manifest and included `policy-trust.json`; run `install.py --check-only` with the actual Hermes interpreter. Stop all consumers for that helper before taking a consistent backup of the original identity/profile, mailbox, collaboration/remote/receipt databases and associated WAL files. Upgrade both matching wheels through the existing installation workflow, update Gateway and desktop backends together, and restart the existing installation. Do not initialize a replacement identity or run old and new consumers against the same database.

The SQLite schema 1-to-2 migration preserves existing records and owner/pairing namespaces. Older runtimes reject an upgraded schema instead of reopening it without review gates. Reinstalling an older wheel or restoring an older database without preserving newer block/review decisions is not a safe rollback. Any offline recovery must retain identity and current safety state. The v0.9.2 full-terms acceptance-card migration and v0.9.3 conversation provenance remain in place.

Existing pairings keep their exact allowed methods and expiry. Explicitly renew or replace the intended owner pairing to add only the required `inbox.review_preview`, `inbox.review`, `contacts.block` and `contacts.unblock` methods; deployment and package installation do not extend authority. Verify the actual capability declaration and perform an existing-identity round trip plus owner review/block checks in the matching host.

Publication, website manifest synchronization, local installation upgrade and a real model/agent outcome are separate checks. This note describes the release behavior; use the deployment release record for actual fixed commits, published asset hashes and verification results.
